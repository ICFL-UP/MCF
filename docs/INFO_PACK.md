# Information Pack: MCF Technical Proof of Concept

## 1. Purpose of This Document

This document consolidates everything required to build the technical proof of concept (PoC) referenced in **Chapter 11** of the dissertation *"The Metaverse Cybersecurity Framework (MCF)"*. It records what the dissertation specifies, fixes the academic scope, captures the underlying technologies, and lists the assumptions that the implementation must respect. It is intentionally scoped: the PoC is described in the dissertation as *"exploratory rather than confirmatory"* and *"a design specification, not a tested system"*. The implementation that follows must therefore be runnable and credible, but not production-grade.

## 2. Position of the PoC Within the Dissertation

The dissertation develops a three-phase Metaverse Cybersecurity Framework (MCF) consisting of (Phase A) six Core Functions adapted from NIST CSF 2.0: Govern, Identify, Protect, Detect, Respond, Recover; (Phase B) organisational Profiles for gap analysis; and (Phase C) four Implementation Tiers. Validation happens in three ways: retrospective MCF application to historical incidents (Chapters 9–10), comparative analysis against ten frameworks (Chapter 12), and prospective scenario evaluation (Chapter 13). The PoC in **Chapter 11** is the *only* technical artifact in the dissertation, and it has a precise role: demonstrate that two MCF Core Functions, **Protect** and **Detect**, can be operationalised as concrete software for the Ronin Bridge scenario examined in Chapter 9. It does not validate the entire framework. Its value is showing that the conceptual recommendations translate into implementable code rather than remaining at the level of prose.

## 3. The Reference Incident: Ronin Bridge Hack (March 2022)

The PoC is grounded in one specific incident, so the implementation must replicate its key parameters faithfully. On 23 March 2022 the Lazarus Group (DPRK-attributed APT38) compromised the Ronin Bridge operated by Sky Mavis, withdrawing 173,600 ETH and 25.5 million USDC across two transactions, approximately $625 million at the time. The bridge operated on a Proof-of-Authority consensus model requiring **five of nine validator signatures** to authorise a withdrawal. The attackers obtained five keys: four Sky Mavis validators (via spear-phishing engineers with a fake LinkedIn job offer carrying a malicious PDF) plus one Axie DAO validator (via a deprecated November 2021 transaction allowlist that had been retained for administrative convenience and provided a backdoor through Ronin's gas-free RPC node). The breach went undetected for **six days**; discovery only happened when a user reported being unable to withdraw 5,000 ETH.

The dissertation isolates two concrete failures that a PoC can directly address: (a) validator credentials had no cryptographic identity binding and no expiration, so once a key was stolen there was no second factor and no time-bounded revocation path; (b) there was no real-time monitoring, so two anomalously large withdrawals went unflagged for a week. These two gaps map cleanly onto MCF's **Protect** and **Detect** functions respectively, which is why the PoC focuses on them.

## 4. Architecture Specified in Chapter 11

Chapter 11.2.1 specifies a three-component architecture with a dual-gate validation pipeline. The first component is a **DID Registry Contract** deployed on an EVM-compatible blockchain. It implements credential lifecycle management for validators using W3C-compliant Decentralised Identifiers via the `did:ethr` method. The contract holds a `ValidatorDID` data structure with the DID string, the bound Ethereum address, an IPFS hash pointing to the off-chain DID Document, a registration timestamp, an expiration timestamp, and an active-status flag. It exposes four operations: `registerValidator` (multisig-gated, must validate that expiration exceeds the current block timestamp); `revokeValidator` (immediate invalidation when compromise is suspected); `renewValidator` (extends validity, multisig-gated); and `verifyValidator` (read-only, returns active status and remaining validity for use during bridge operations). The multisig requirement is what ties the Protect function back to MCF's Govern function: no single administrator can grant or extend privileges.

The second component is a **Validator Authentication Module** that binds signing keys to the DIDs registered above. In the dissertation this is presented as a separate logical module, but it is essentially the on-chain verification layer: when a bridge transaction arrives, it must carry a signature whose recovered address matches a `ValidatorDID` that is currently active and unexpired.

The third component is an off-chain **Transaction Monitoring Service** implementing the Detect function via statistical anomaly detection. It maintains a rolling baseline of normal activity covering average transaction values, daily withdrawal volumes, and destination-address frequency. For each new transaction it computes a composite anomaly score weighting three factors: (i) value deviation from the 30-day rolling mean, (ii) volume deviation from the daily baseline, and (iii) destination-address novelty (transfers to previously unseen addresses score higher). Two thresholds are applied: a *configured* threshold triggers an alert; a *critical* threshold triggers automatic bridge pause pending manual review.

The dissertation is explicit that these three components form a **dual-gate validation pipeline**. Every bridge transaction must pass both the cryptographic authentication check against the validator's DID *and* the anomaly evaluation. Failure of either check triggers MCF's Respond protocols. This defence-in-depth design is the core claim of the PoC: even if an attacker compromises validator keys (defeating the Protect gate as in the original Ronin incident), the Detect gate should catch the anomalous withdrawal pattern; conversely, even if an attacker tries to disguise withdrawals to evade Detect, they still need to defeat Protect first.

## 5. What the PoC Must Demonstrate Against the Ronin Scenario

The dissertation makes concrete, testable claims about how the proposed system would have behaved on 23 March 2022. The Lazarus Group transactions involved 173,600 ETH, *"far beyond normal withdrawal patterns. This would register as extremely high deviation under any reasonable baseline, triggering both alert and automatic suspension. The six-day detection lag in the actual case would be reduced to seconds in this design."* The credential-lifecycle argument is equally specific: the deprecated November 2021 allowlist would not have persisted because *"all validator credentials carry explicit expiration dates and require active renewal. Indefinite persistence of temporary permissions is eliminated by default."* These are the two empirical claims the PoC must demonstrate: sub-second detection of a Ronin-scale outflow, and automatic invalidation of stale credentials.

The dissertation also acknowledges what the PoC *cannot* claim: it does not address the false-positive rate, it does not validate behaviour against pattern-based attacks that evade simple statistical baselines, and it has not been tested against unseen threat scenarios. These limitations are part of the academic framing and should be reproduced in the implementation's documentation and discussion.

## 6. Established Techniques the Implementation Builds On

The dissertation is deliberate about positioning: *"This architecture does not address novel technical problems. Decentralised identifiers, multisig governance, and statistical anomaly detection are established techniques. The design value lies in their combined application to the specific validator problem rather than in technical novelty."* This framing matters for implementation choices; there is no requirement to invent new cryptography or new ML, only to combine known building blocks correctly. The cited reference points are: W3C DIDs v1.0 (Recommendation, July 2022), the `did:ethr` method (ERC-1056 / Decentralized Identity Foundation reference resolver), self-sovereign identity surveys (Sovrin, uPort, Jolocom, ShoCard), YouGovern's BSC deployment (0.94-second registration latency), ensemble fraud-detection methods (XGBoost + Random Forest), the Elliptic++ dataset (203k Bitcoin transactions, 822k addresses, 166 features per node) for training baselines, and recent spatial-temporal GNN work reaching F1 ≈ 0.92. The implementation does not need to reproduce GNN-grade performance; the dissertation explicitly says the statistical baseline is sufficient for the PoC, with sophisticated detectors mentioned only as a literature reference.

Recent work specific to bridge security adds context the implementation can cite: **XChainWatcher** retrospectively detected the Ronin attack pattern in telemetry; **BridgeGuard** proposed a two-stage detection framework with 36.32% better recall than prior systems; **Hephaestus** introduced a cross-chain monitoring model generator. These three are referenced [199–201] in the dissertation as evidence that bridge monitoring is a recognised research priority; the PoC sits in the same line of work, not in opposition to it.

## 7. Academic Constraints Shaping Implementation Choices

This is a Master's CS dissertation, not a startup pitch. Three constraints follow. First, the work must be **reproducible by an examiner**: a self-contained repository runnable from a single command on a standard developer machine, ideally without paid services or testnets. Second, the work must be **honest about scope**: the PoC is partial by design, so the documentation should mirror the dissertation's own caveats rather than overstating capability. Third, the work must be **defensible in a viva**: every design choice should map back either to the dissertation's text or to a cited reference, and trade-offs should be articulated. These three constraints justify a path-of-least-resistance approach: a local Hardhat (or Foundry) network, a small Solidity codebase, a Python monitoring service, synthetic transaction data based on Ronin's published parameters, and a clearly written README.

## 8. Path-of-Least-Resistance Stack

The recommended stack is deliberately conservative and uses only mature, well-documented components. For the on-chain layer, **Solidity ^0.8.20** with **OpenZeppelin** contracts (for `Ownable`, `AccessControl`, and `ECDSA`) and the **Hardhat** development framework. Hardhat is preferred over Foundry for this project because the off-chain monitoring service is in Python and Hardhat's JSON-RPC integration is the most thoroughly documented across both ecosystems; Foundry would also work and is faster for tests, but its Solidity-only test culture adds a small learning tax with no academic benefit here. The local **Hardhat Network** is used in place of any testnet: it is free, deterministic, and resets cleanly between runs.

For the off-chain layer, **Python 3.11+** with **web3.py** for chain interaction, **NumPy** for the rolling baseline arithmetic, **pandas** for data shaping during analysis, and **pytest** for tests. A small CLI orchestrator stitches deployment, validator registration, transaction replay, and monitoring into a single reproducible scenario script. **Matplotlib** generates the figures the dissertation can reference (detection-time histograms, anomaly-score distributions, baseline-vs-attack overlays). No machine-learning libraries are required; the dissertation explicitly uses simple statistical detection.

A `did:ethr`-compatible identifier is constructed at registration time as `did:ethr:<chainId>:<validatorAddress>`, which is the format defined in the ERC-1056 specification. The PoC does not need to deploy the full upstream `ethr-did-registry` contract; it implements a simpler, MCF-specific registry with the four operations the dissertation specifies. The DID Document hash field is populated with the SHA-256 of a locally generated JSON document conforming to the W3C DID Core data model; IPFS itself is not required for the PoC. This is a defensible simplification: the dissertation's argument is about credential lifecycle and binding, not about decentralised storage of DID documents.

## 9. Validation Strategy

Validation is built around three reproducible scenarios that each map to a specific claim in Chapter 11. **Scenario 1: Credential Lifecycle.** A validator is registered, transacts successfully, then has its credential expire; subsequent transactions are rejected at the Protect gate. A second sub-case revokes a credential mid-flight to simulate a compromise response. This scenario demonstrates the *"indefinite persistence of temporary permissions is eliminated by default"* claim and the multisig-gated lifecycle operations.

**Scenario 2: Ronin-Scale Outflow Detection.** A 30-day synthetic baseline of bridge withdrawals is generated with a value distribution and destination-address pattern calibrated to publicly reported pre-attack Ronin activity. The actual Ronin transactions (173,600 ETH and ≈25.5M USDC, both to the attacker's deposit address) are then injected. The monitoring service must produce an alert and trigger automatic bridge pause within a single block of the first malicious transaction. This is the headline claim (*"reduced to seconds in this design"*), and it produces the most quotable result.

**Scenario 3: Composite Score Stress Tests.** A set of edge-case inputs probes the three weighted factors individually: (i) a high-value transaction to a *known* destination should score lower than the same value to a novel destination; (ii) a single anomalous-volume day with all-known destinations should score below the critical threshold but above the alert threshold; (iii) a structuring attack splitting Ronin's outflow across many smaller transactions should still raise the volume-deviation factor. This scenario probes the limits the dissertation itself flags (*"a monitoring system tuned to catch massive outliers may miss smaller coordinated attacks"*), and gives material for the discussion section.

Each scenario produces a deterministic numerical output (block number, anomaly score, threshold hit) and a generated figure. The combined output forms the basis of an `evaluation.md` report alongside the implementation.

## 10. Risks and Limitations

The PoC inherits the dissertation's own self-acknowledged limitations and should not paper over them. The statistical detector uses synthetic data calibrated to public reports; it has not been tuned on real exchange-grade transaction logs. False-positive rate on production traffic is unknown. The multisig used in the registry is a minimal m-of-n owner set, not a Gnosis-Safe-grade implementation (sufficient for an academic PoC, not for mainnet). The `did:ethr` integration follows the ERC-1056 identifier format but uses a simplified registry rather than the upstream resolver, which means a third-party `did:ethr` resolver would not natively resolve PoC DIDs without configuration. None of these limitations weaken the dissertation's claims, because Chapter 11 explicitly bounds the scope to a design specification rather than a deployment-ready system. Documenting them transparently strengthens the academic credibility of the artifact.

## 11. Mapping Back to the Dissertation Text

For viva defensibility, every implementation file should be traceable to a specific paragraph in Chapter 11. The DID Registry contract corresponds to Section 11.2.2 (DID-Based Validator Identity); the four function signatures (`registerValidator`, `revokeValidator`, `renewValidator`, `verifyValidator`) appear verbatim in the dissertation. The `ValidatorDID` struct field list (DID string, bound address, IPFS hash, registration timestamp, expiration timestamp, active flag) is also given verbatim and must match exactly. The composite-score weighting (value deviation, volume deviation, destination novelty) is from Section 11.2.3, as is the two-threshold alert/pause behaviour and the 30-day rolling baseline window. The dual-gate pipeline is from Section 11.2.4. The Ronin numerical parameters (5-of-9 validators, 173,600 ETH, 25.5M USDC, six-day detection lag) come from Section 9.2. Anchoring the code to these exact text references is the simplest way to defend each design decision in examination.
